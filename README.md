# Bosch eBike – Home Assistant add-on

> [!WARNING]
> **Early version.** Tested on one bike so far. Part of it talks to the bike
> over an undocumented channel, and things may change between versions.

A Home Assistant add-on for Bosch smart system eBikes. It runs on the HA
host's Bluetooth (no ESP32), finds the bike by itself and shows everything on
one page in Home Assistant. It reads the bike two ways, both read-only:

- the official **Live Data Interface (LDI)**: battery %, speed, cadence,
  rider power, odometer, charger, lights;
- **MCSP**, the Flow app's own channel: battery health and cycles,
  temperatures, motor hours, software versions, range per assist mode, the
  bike's ride computer and its messages.

From those it builds charging and riding stats (time to full, energy per km,
range the way you ride), and it compares each component's firmware with
Bosch's published versions (information only, never installs).

User documentation: [bosch_ebike_ldi/DOCS.md](bosch_ebike_ldi/DOCS.md).
How it works: [DESIGN.md](DESIGN.md). Where details came from:
[SOURCES.md](SOURCES.md).

## Layout

```
repository.yaml               add-on repository marker
bosch_ebike_ldi/              the add-on
  config.yaml, Dockerfile, run.sh, DOCS.md, CHANGELOG.md, translations/
  app/bridge.py               orchestration: BlueZ/D-Bus, LDI accessory, pairing agent,
                              checks and full readings, state, wiring
  app/explorer.py             one MCSP session per bike: handshake, reads, sweep
  app/mcsp.py                 MCSP framing, messages, read-only safety check (pure)
  app/datapoints.py           datapoint table, decoding, read lists, HA entities (pure)
  app/datapoints.json         generated by scripts/build_datapoints.py
  app/faults.py, faults.json  Bosch fault codes (generated by scripts/build_faults.py)
  app/protowire.py            schema-less protobuf decoding (pure)
  app/livedata.py             LDI decoder, charge-time and energy estimates
  app/stats.py                charging and riding history (pure)
  app/webui.py                the add-on's page (Home Assistant ingress)
  app/device_info.py          Device Information service the Flow app shows
  app/ha_mqtt.py              Home Assistant MQTT discovery and state
  app/ble_policy.py           shared-adapter rules, advert parsing (pure)
  app/nearby.py               Bosch bikes heard nearby (pure)
  app/status.py               status texts (pure)
  app/firmware.py             Bosch's published versions: parse, match, compare
  app/supervisor.py           Supervisor: MQTT lookup, HA notifications
  app/capture.py              per-run debug capture and report.json
  app/options.py              add-on options -> config (pure)
scripts/test.sh               build the image and run every test inside it
scripts/build_*.py            regenerate the generated tables from the protocol notes
tests/                        unit tests (any OS)
tests/integration/            real bridge vs a fake BlueZ + fake Bosch bike + mosquitto
```

## Testing

```sh
# Unit tests on any machine
py -3.13 -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt
.venv/Scripts/python -m pytest tests

# Everything, inside the real add-on image (needs Docker)
sh scripts/test.sh                # amd64
sh scripts/test.sh linux/arm64    # Raspberry Pi architecture, via emulation
```

The integration tests run the real `bridge.py` against `fake_bluez.py`, a
fake BlueZ with a fake Bosch bike that speaks MCSP, written independently of
`mcsp.py`. The fake bike behaves like the real one where it matters: it
answers MCSP only on links the add-on opens, advertises the way the real bike
does, and bonds only while the adapter is pairable. The tests cover:

- the journey: no bike, bike heard nearby, added, status, device info,
  firmware update entity, notifications once across restarts;
- LDI pairing and data;
- checks when the bike advertises (charging: full reading; not charging: let
  go), the full-reading window and its time limit;
- the read-only guarantee: every byte sent is checked, there are no requests
  to command datapoints, and the sweep covers exactly the readable table;
- NOT_READY and OVERLOADED handling, silent links, source-address fallback;
- the page, its actions and downloads;
- range, messages, ride computer, charging and riding stats;
- the capture and report contents.

Behaviour against a real bike, real BlueZ and the Flow app has been checked
by hand on one bike; see the changelog.
